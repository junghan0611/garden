### Rise and shine, Dr.Diffman. Rise and shine. {#rise-and-shine-dr.-diffman.-rise-and-shine.}

일어나세요, 디프맨 박사. 일어나세요.

If you load a file that's tracked via version control into your editor, most modern text or code editors will indicate in the buffer the bits that have been modified since the last commit, i.e.the last set of registered changes. Here's the [Zed editor](https://zed.dev/) showing this via yellow/red marks in the fringe to the left of the text:<br />

파일을 버전 관리로 추적되는 상태에서 편집기에 로드하면, 대부분의 현대 텍스트 또는 코드 편집기는 마지막 커밋 이후 수정된 부분, 즉 마지막으로 등록된 변경 사항을 버퍼에 표시합니다. 다음은 Zed 편집기가 텍스트 왼쪽 가장자리에 노란색/빨간색 표시로 이를 보여주는 모습입니다:

{{< figure src="/images/zed-diff-hl.png" >}}

Emacs에서는 Dmitry Gutov의 diff-hl 또는 Shohei Yoshida의 git-gutter 패키지를 통해 제공되며, 여기에는 전자가 표시되어 있습니다:

{{< figure src="/images/emacs-diff-hl.png" >}}

This inline-indication business usually goes _much_ further, with editors annotating lines with when they were last changed, or whose fault it was. My relatively tiny code or prose projects with 2-4 participants (at most) have little need for these fancier features. Emacs makes it easy enough to generate them when required anyway<br /> 이 인라인 표시 비즈니스는 보통 더 나아가, 편집자들이 마지막으로 변경된 시점이나 누가 잘못했는지를 주석으로 달곤 합니다. 저의 상대적으로 작은 코드나 산문 프로젝트는 2-4명의 참가자(최대)로 구성되어 있어 이러한 고급 기능이 필요하지 않습니다. 어쨌든 Emacs는 필요할 때 이를 생성하는 것을 충분히 쉽게 만들어 줍니다. vc-region-history (C-x v h) and vc-annotate (C-x v g), respectively -- no Magit required.vc-region-history ( C-x v h ) 및 vc-annotate ( C-x v g ), 각각 -- Magit 필요 없음. .

But diff-hl is mighty handy. Being able to identify changed regions at a glance is good, but you can also navigate and act on them. Jump between hunks with one key, see changes inline, mark or revert hunks and more:<br /> 하지만 diff-hl은 매우 유용합니다. 변경된 영역을 한눈에 식별할 수 있는 것은 좋지만, 이를 탐색하고 조치를 취할 수도 있습니다. 한 키로 덩어리 간에 점프하고, 인라인에서 변경 사항을 확인하며, 덩어리를 표시하거나 되돌리는 등의 작업을 할 수 있습니다.

[[VIDEO: diff-hl demo][비디오: diff-hl 데모](https://karthinks.com/img/emacs-diff-hl-demo.mp4%22)] Play by play

The keys being pressed are indicated in the header.<br /> 헤더에 눌리고 있는 키가 표시됩니다.

-   With `diff-hl-mode` enabled in the buffer,<br /> 버퍼에서 `diff-hl-mode` 가 활성화되어 있습니다
-   Run `diff-hl-next-hunk` (`C-x v n`). This moves the cursor to the next hunk,<br /> 다음 덩어리로 커서를 이동하려면 `diff-hl-next-hunk` ( `C-x v n` )을 실행하세요.
-   and it activates a [repeat-map](https://karthinks.com/software/it-bears-repeating/), making subsequent diff-hl commands accessible with just `n`, `p` and so on.<br /> 그리고 반복 맵을 활성화하여 이후의 diff-hl 명령을 `n` , `p` 등으로 쉽게 접근할 수 있게 합니다.
-   Press `*` (shortened from `C-x v *` by `repeat-mode`) to show inline diffs of changed hunks.<br /> `*` 를 눌러 변경된 덩어리의 인라인 차이를 표시합니다 ( `C-x v *` 에서 `repeat-mode` 만큼 축약됨).
-   After navigating some more, press `SPC` (shortened from `C-x v SPC` by `repeat-mode`) to mark a hunk.<br /> 조금 더 탐색한 후, `repeat-mode` 로 `C-x v SPC` 에서 축약된 `SPC` 를 눌러 덩어리를 표시하세요.


### The right diff in the wrong place... {#the-right-diff-in-the-wrong-place}

잘못된 위치에 있는 올바른 차이...

There's only one problem: when working on a branch with many commits, diff-hl tracks changes relative to the `HEAD` of the branch. This is almost never what I want when I'm working on a feature off in a different branch. Representing each commit as a sphere, here's what I mean:<br /> 유일한 문제는 많은 커밋이 있는 브랜치에서 작업할 때 diff-hl이 브랜치의 `HEAD` 에 대한 변경 사항을 추적한다는 것입니다. 이는 다른 브랜치에서 기능 작업을 할 때 거의 항상 제가 원하는 것이 아닙니다. 각 커밋을 구체로 표현하면, 제가 의미하는 바는 다음과 같습니다:

{{< figure src="Fringe%20Matters%20Finding%20the%20Right%20Difference%20%20Karthinks/diff-hl-default-revision-tree.png" >}}

At this stage, the change from `feature` / `HEAD` to the worktree is at best an incomplete picture. Unless looking for something very specific, it doesn't help to highlight worktree changes against earlier commits on `feature` either. The previous commits in this branch are temporary checkpoints in an experiment, and don't necessarily represent atomic, self-contained or meaningful changes -- hence the jumble of colors in each commit in the figure. What I find actually helpful is to compare the contents of the buffer to the state of the _main branch_:<br /> 이 단계에서 `feature` / `HEAD` 에서 작업 트리로의 변화는 최선의 경우 불완전한 그림에 불과합니다. 매우 구체적인 것을 찾지 않는 한, `feature` 에서 이전 커밋에 대한 작업 트리 변경 사항을 강조하는 것은 도움이 되지 않습니다. 이 브랜치의 이전 커밋은 실험의 임시 체크포인트이며, 반드시 원자적이고 독립적이며 의미 있는 변화를 나타내는 것은 아닙니다. 따라서 그림의 각 커밋에서 색상이 뒤섞여 있는 것입니다. 제가 실제로 유용하다고 생각하는 것은 버퍼의 내용을 메인 브랜치의 상태와 비교하는 것입니다.

{{< figure src="Fringe%20Matters%20Finding%20the%20Right%20Difference%20%20Karthinks/diff-hl-customized-revision-tree.png" >}}

This is, of course, readily accessible via Magit or VC via a couple of keystrokes. Either one can produce pleasingly formatted diff buffers showing the right changes for any range. But as mentioned above, being able to have the right changes indicated in the work buffer is only one of the advantages. With diff-hl and the right range of changes indicated, you can jump between them, mark them, revert them and more.<br /> 물론, 이는 몇 번의 키 입력으로 Magit 또는 VC를 통해 쉽게 접근할 수 있습니다. 두 가지 모두 어떤 범위에 대한 올바른 변경 사항을 보여주는 보기 좋게 포맷된 diff 버퍼를 생성할 수 있습니다. 그러나 위에서 언급했듯이 작업 버퍼에 올바른 변경 사항이 표시되는 것은 장점 중 하나일 뿐입니다. diff-hl과 올바른 변경 범위가 표시되면, 그 사이를 이동하고, 표시하고, 되돌리고, 그 외에도 여러 가지 작업을 수행할 수 있습니다.

Recreating the commits in `feature` to encode atomic -- or at least limited -- changes is on the docket, but for later. This involves "unscrambling" the commits into uniformly colored spheres, often via an interactive rebase, or just selective git-resets:<br /> `feature` 의 커밋을 원자적이거나 최소한 제한된 변경 사항으로 인코딩하기 위해 재구성하는 것은 나중에 진행할 예정입니다. 이는 커밋을 균일한 색상의 구체로 "풀어내는" 작업을 포함하며, 종종 인터랙티브 리베이스를 통해 이루어지거나 선택적인 git-reset을 통해 수행됩니다.

{{< figure src="Fringe%20Matters%20Finding%20the%20Right%20Difference%20%20Karthinks/diff-hl-cleanup-commits.png" >}}

Usually the true "shape" of the changes can only be limned at the end of the `feature` experiment, at which point a "logical" history can be forged before merging into the main branch using your preferred strategy<br /> 보통 변화의 진정한 "형태"는 `feature` 실험의 끝에서만 윤곽을 드러낼 수 있으며, 이 시점에서 선호하는 전략을 사용하여 주요 분기로 통합하기 전에 "논리적인" 역사를 형성할 수 있습니다 Unless your preferred strategy is to squash all the carefully recreated, atomic commits into a giant merge commit. Then your preferred strategy is wrong.당신이 선호하는 전략이 모든 정교하게 재구성된 원자 커밋을 거대한 병합 커밋으로 압축하는 것이라면, 당신의 선호 전략은 잘못된 것입니다. .

{{< figure src="Fringe%20Matters%20Finding%20the%20Right%20Difference%20%20Karthinks/diff-hl-merge-strategy.png" >}}


### ...can make all the difference in the world. {#can-make-all-the-difference-in-the-world.}

...세상에 모든 차이를 만들 수 있습니다.

As it turns out diff-hl understands this problem to a limited extent. It provides a secondary minor-mode, `diff-hl-amend-mode`, that shows the change markers with respect to `HEAD^`, the parent of `HEAD`. This is typically what you want when your changes are intended to amend the latest commit instead of creating a new one. While it's not what we're looking for, it's a good starting point.<br /> 결국 diff-hl은 이 문제를 제한된 정도로 이해합니다. 그것은 `HEAD` 의 부모인 `HEAD^` 에 대한 변경 마커를 보여주는 보조 마이너 모드 `diff-hl-amend-mode` 를 제공합니다. 이는 일반적으로 변경 사항이 새로운 커밋을 만드는 대신 최신 커밋을 수정하려는 경우에 원하는 것입니다. 우리가 찾고 있는 것은 아니지만, 좋은 출발점입니다.

But the mechanism is simple enough. In this pseudo Elisp block:<br /> 하지만 메커니즘은 충분히 간단합니다. 이 가짜 Elisp 블록에서:

```emacs
(show-changes-between from-commit current-buffer-state)
```

we'd like a way to set `from-commit`, but just for this buffer or project. If you use `diff-hl-amend-mode`, `from-commit` would be `HEAD^`. If we can set it to `master` or `master^` (or `main`), we're done.<br /> 우리는 `from-commit` 를 설정할 수 있는 방법이 필요하지만, 이 버퍼나 프로젝트에만 해당됩니다. `diff-hl-amend-mode` 을 사용하면 `from-commit` 는 `HEAD^` 이 될 것입니다. `master` 또는 `master^` (또는 `main` )로 설정할 수 있다면, 우리는 완료됩니다.

And set it we can. `from-commit` is actually a single global variable conveniently exposed by diff-hl: `diff-hl-reference-revision`. We can deal with the globality by making it buffer local. And that's it as far as the Elisp hacking goes -- no hooks or advice needed today.<br /> 그리고 우리는 그것을 설정할 수 있습니다. `from-commit` 는 실제로 diff-hl에 의해 편리하게 노출된 단일 전역 변수입니다: `diff-hl-reference-revision` . 우리는 그것을 버퍼 로컬로 만들어 전역성을 처리할 수 있습니다. 그리고 그것이 Elisp 해킹에 관한 전부입니다 -- 오늘은 후크나 조언이 필요하지 않습니다.


### Not that I wish to imply you have been sleeping on the margins. {#not-that-i-wish-to-imply-you-have-been-sleeping-on-the-margins.}

당신이 여백에서 잠을 자고 있었다고 암시하고 싶은 것은 아닙니다.

Only there's still the matter of the interface. The absolute spartan way of using this option would be to run `M-x eval-expression` (`M-:`) and type in<br /> 여전히 인터페이스 문제는 남아 있다. 이 옵션을 사용하는 절대적으로 간소한 방법은 `M-x eval-expression` ( `M-:` )를 실행하고 입력하는 것이다.

```emacs
(setq-local diff-hl-reference-revision "master")
```

On later uses, you can search the minibuffer history for this code via `minibuffer-complete-history` (`M-r`). After a few weeks of this, the mild frustration mounts until it crosses a threshold: _I should really put this somewhere more convenient_.<br /> 나중에 사용할 때, 이 코드를 `minibuffer-complete-history` ( `M-r` )를 통해 미니버퍼 기록에서 검색할 수 있습니다. 몇 주가 지나면서, 약간의 불만이 쌓이다가 어느 순간 한계를 넘습니다: 이걸 좀 더 편리한 곳에 두어야 할 것 같습니다.

The logical next step is to define a command that does this. diff-hl actually includes one<br /> 논리적인 다음 단계는 이를 수행하는 명령을 정의하는 것입니다. diff-hl은 실제로 하나를 포함하고 있습니다. It's diff-hl-set-reference-rev , but that sets it globally, across Emacs. So we sigh and grow our configuration files a little bit:<br /> 하지만 이는 Emacs 전역에 설정됩니다. 그래서 우리는 한숨을 쉬고 구성 파일을 조금 더 늘립니다.

```emacs
(defun my/diff-hl-set-reference () "Set the reference revision for showing diff-hl changes. Do so buffer-locally." (interactive) (setq-local diff-hl-reference-revision (read-string (format "Set reference revision (buffer %s): " (buffer-name)))) (diff-hl-update))
```

Dust your hands, the problem's solved. `M-x my/diff-hl-set-reference` works pleasingly for a few weeks, especially since the minibuffer completion system floats this up with frequent usage<br /> 손에 먼지를 털어내세요, 문제는 해결되었습니다. `M-x my/diff-hl-set-reference` 는 몇 주 동안 기분 좋게 작동하며, 특히 미니버퍼 완성 시스템이 자주 사용되면서 이를 부각시킵니다. You do use savehist-mode or prescient, right?당신은 savehist-mode 또는 prescient 을 사용하죠? for easy access.

But eventually two further needs appear:<br /> 하지만 결국 두 가지 추가적인 필요가 나타납니다:

1.  I use this so often that I need it on a key, dammit.<br /> 이걸 너무 자주 사용해서 열쇠에 달아야겠어, 젠장.
2.  Can't I just set this across my project instead of in every buffer?<br /> 이것을 모든 버퍼 대신 프로젝트 전반에 걸쳐 설정할 수는 없나요?

Needs 1 and 2 obviate each other somewhat, in that either one makes it less necessary to call the `-set-reference` command via `M-x`. But let's address them separately anyway.<br /> 요구 사항 1과 2는 서로 어느 정도 상쇄되는데, 이는 어느 하나가 `M-x` 을 통해 `-set-reference` 명령을 호출할 필요성을 줄이기 때문입니다. 하지만 어쨌든 각각 따로 다뤄보겠습니다.


#### All the effort in the world would have gone to waste until... {#all-the-effort-in-the-world-would-have-gone-to-waste-until}

세상의 모든 노력이 헛되이 사라졌을 것이다, 만약...

Setting up a keybind is easy if we can find room for it. And then if we can remember it. Emacs keymaps are crowded spaces. On more than one occasion I've opened up my init file intending to add a handy keybinding for a useful command, only to discover that I already did months ago... and then forgot it was available.<br /> 키 바인딩을 설정하는 것은 공간이 있다면 쉽습니다. 그리고 그것을 기억할 수 있다면 더욱 그렇습니다. Emacs 키맵은 혼잡한 공간입니다. 유용한 명령을 위한 편리한 키 바인딩을 추가할 생각으로 init 파일을 열었지만, 몇 달 전에 이미 추가했음을 발견하고 그것이 사용 가능하다는 것을 잊어버린 적이 여러 번 있습니다.

To some extent you can mitigate this effect by placing it logically with the other diff-hl commands, which are conveniently grouped together into `diff-hl-command-map`. So assuming you use _any_ diff-hl commands, this one should show up in `which-key` or your keymap prompter of choice.<br /> 어느 정도는 이 효과를 다른 diff-hl 명령어들과 논리적으로 배치함으로써 완화할 수 있습니다. 이 명령어들은 편리하게 `diff-hl-command-map` 에 함께 그룹화되어 있습니다. 따라서 diff-hl 명령어를 사용하는 경우, 이 명령어는 `which-key` 또는 선택한 키맵 프롬프터에 나타나야 합니다.

But in my case even this is a lost cause. I already combine `vc-prefix-map`, used by Emacs for version control actions, with `diff-hl-command-map` under the `C-x v` prefix because their functions are related. So `C-x v` is quite a busy junction. Here's which-key doing its best to show me what's available:<br /> 하지만 제 경우에는 이것조차도 헛수고입니다. 저는 이미 Emacs에서 버전 관리 작업에 사용되는 `vc-prefix-map` 와 `diff-hl-command-map` 을 `C-x v` 접두사 아래에서 결합하고 있습니다. 그들의 기능이 관련이 있기 때문입니다. 그래서 `C-x v` 는 꽤 바쁜 교차로입니다. 여기서 which-key가 제가 사용할 수 있는 것들을 보여주기 위해 최선을 다하고 있습니다:

The solution is to place it where I turn on/off `diff-hl-mode` in the first place: in a catchall transient menu I use to access all minor-modes I need in Emacs buffers<br /> 해결책은 내가 Emacs 버퍼에서 필요한 모든 부모드를 접근하기 위해 사용하는 포괄적인 임시 메뉴에 `diff-hl-mode` 를 켜고 끄는 곳에 두는 것입니다 A good chunk of this menu deals with settings that make no sense for most Emacs users -- for example, a switch to toggle requiring sentence ends to be single/double spaced, adjust line-spacing on the fly, or switch between different sets of CAPFs.이 메뉴의 상당 부분은 대부분의 Emacs 사용자에게는 의미가 없는 설정을 다룹니다. 예를 들어, 문장 끝을 단일/이중 간격으로 요구하는 전환 스위치, 즉석에서 줄 간격을 조정하는 기능, 또는 다양한 CAPF 세트 간 전환 등이 있습니다.

Calling the diff-hl option from this menu with a prefix-arg now (essentially) runs the above function, allowing me to set the reference revision before turning on the mode (if required).<br /> 이 메뉴에서 prefix-arg와 함께 diff-hl 옵션을 호출하면 이제 (본질적으로) 위의 함수를 실행하여 모드를 켜기 전에 참조 개정을 설정할 수 있습니다(필요한 경우).

Here's a demo combining this with a few other nifty diff-hl commands and [repeat-mode](https://karthinks.com/software/it-bears-repeating/):<br /> 여기 몇 가지 다른 유용한 diff-hl 명령어와 반복 모드를 결합한 데모가 있습니다:

[[VIDEO: Toggling diff-hl reference revision](https://karthinks.com/img/diff-hl-toggle-modes-demo.mp4%22)] Play by play

The keys being pressed are indicated at the top.

-   Begin in a buffer in some feature branch that is some "distance" away from `master`.
-   Use diff-hl commands to navigate to hunks. diff-hl is currently showing buffer changes in the working tree against `HEAD`.
-   Use `diff-hl-show-hunk` (`C-x v *`) to see the diffs for individual hunks inline.
-   Call the `toggle-modes` transient mentioned above.
-   Choose the `g` option with a prefix-arg (`C-u`). This causes the reference revision (the `from-commit` we want) to be read from the minibuffer. Ask to see changes from `master`.
-   diff-hl updates to mark changes from `master`. As you might expect, there are more changes -- everything that's changed since `master`.
-   Navigate through the changes again with diff-hl commands.
-   Pick the `toggle-modes` transient menu option again, this time setting the reference revision to `HEAD`'s grandparent, `HEAD^^`.
-   diff-hl updates the changes again. As you might expect, there are fewer changes.

Here's the actual function that `g` in the `toggle-modes` menu is bound to:<br /> 여기 `toggle-modes` 메뉴에서 `g` 에 바인딩된 실제 기능이 있습니다:

```emacs
(lambda (&optional arg) "Toggle `diff-hl-mode'. With prefix ARG ensure `diff-hl-mode' and set revision to compare against." (interactive "P") (if (null arg) (diff-hl-mode 'toggle) (let ((ref (read-string "Reference revision for diff-hl: "))) (setq-local diff-hl-reference-revision ref) (diff-hl-mode) (diff-hl-update) (message "Showing changes against %s" ref))))
```


#### ...well, let's just say your hour has come again. {#well-lets-just-say-your-hour-has-come-again.}

...글쎄, 당신의 시간이 다시 왔다고만 하죠.

As you might expect, the way to apply diff-hl's reference revision setting to all buffers in a project is to use a [directory-local variable](https://www.gnu.org/software/emacs/manual/html_node/emacs/Directory-Variables.html). In most cases, setting it once per project (or git-worktree, in my case) is all you need.<br /> 당연히 예상할 수 있듯이, diff-hl의 참조 수정 설정을 프로젝트의 모든 버퍼에 적용하는 방법은 디렉토리 로컬 변수를 사용하는 것입니다. 대부분의 경우, 프로젝트(또는 제 경우에는 git-worktree)당 한 번만 설정하면 충분합니다.

This approach requires a little forethought but no moment-to-moment busywork: Run `M-x add-dir-local-variable`<br /> 이 접근 방식은 약간의 사전 고려가 필요하지만 순간순간의 바쁜 작업은 필요하지 않습니다: `M-x add-dir-local-variable` 실행

-   with a major-mode choice of `nil`,<br /> 주요 모드 선택이 `nil` 인 경우,
-   and setting the variable `diff-hl-reference-revision`<br /> 변수 `diff-hl-reference-revision` 설정하기
-   to `"master"` .

This produces the following `.dir-locals.el` file:<br /> 다음 `.dir-locals.el` 파일이 생성됩니다:

```emacs
;;; Directory Local Variables -*- no-byte-compile: t -*- ;;; For more information see (info "(emacs) Directory Variables") ((nil . ((diff-hl-reference-revision . "master"))))
```

Typically you would want to chuck this file into version control as well -- but in this case that may be something you want to consider carefully!<br /> 일반적으로 이 파일을 버전 관리에 포함시키고 싶겠지만, 이 경우에는 신중하게 고려해야 할 사항일 수 있습니다!


### So, wake up, Dr.Diffman. Wake up and mark the fringes. {#so-wake-up-dr.-diffman.-wake-up-and-mark-the-fringes.}

자, 일어나세요, 디프먼 박사. 일어나서 가장자리를 표시하세요.

Before I thought to adapt diff-hl to how I worked, I was coding in feature branches in a strange way. I would make a bunch of work-in-progress checkpoint commits and store them on a remote, then soft-reset the branch to the original branch point so I could see indicators for all changed regions in buffers, jump between them with `diff-hl-next-hunk` and so on.<br /> 내가 diff-hl을 내 작업 방식에 맞게 조정하기 전에, 나는 특성 브랜치에서 이상한 방식으로 코딩하고 있었다. 나는 작업 중인 체크포인트 커밋을 여러 개 만들고 이를 원격에 저장한 다음, 브랜치를 원래 브랜치 지점으로 소프트 리셋하여 버퍼에서 변경된 모든 영역에 대한 표시기를 볼 수 있도록 하고, `diff-hl-next-hunk` 을 사용하여 그 사이를 이동하는 식이었다.

It took a while a "while" is code for years"while"은 수년을 의미하는 코드입니다 to consider that it didn't have to be this way. This isn't an adjustment that requires Emacs' much vaunted flexibility -- you can probably do this in any editor that provides the diff-hl feature. I just never thought to do it, and worked around the tool instead of making the tool work for me. Well that's sorted.<br /> 이렇게 될 필요는 없었다는 것을 고려해야 한다. 이것은 Emacs의 자랑스러운 유연성이 필요한 조정이 아니다. diff-hl 기능을 제공하는 어떤 편집기에서도 아마 할 수 있을 것이다. 나는 그럴 생각을 하지 않았고, 도구가 나를 위해 작동하도록 만들기보다는 도구를 우회해서 사용했다. 잘 해결되었다.

There is no other upshot. This yak has been shaved. You're free now, go mark some fringes.<br /> 다른 결과는 없다. 이 야크는 깎였다. 이제 자유다, 가장자리를 표시하러 가라.
