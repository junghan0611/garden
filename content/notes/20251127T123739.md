```markdown
알겠습니다. "bd는 단순한 todo 도구가 아니다"라는 말씀과, 멀티-에이전트 환경에서 tasks.md와 bd를 어떻게 유기적으로 활용하여 Claude 팀(Opus 모델)의 짧은 컨텍스트 문제를 해결할 것인가에 대한 깊은 고민에 전적으로 동감합니다.

tasks.md가 "dummy 데이터"가 되지 않게 하려면, /speckit.taskstoissues 명령이 실행될 때, 각 태스크에 관련된 모든 정보를 bd 이슈의 description 필드에 체계적으로 집어넣어야 합니다.

1. tasks.md 템플릿 강화
현재 tasks.md 템플릿에 컨텍스트 주입을 위한 필드를 추가해야 합니다.
강화된 템플릿:
- T(번호): [태스크 이름]
  - bd: (생성 전 비워둠)
  - *아키텍처 컨텍스트*:
    - `[관련 아키텍처 문서:섹션]` (예: `main_loop_architecture.md#UI/LED-제어`)
  - *참조 (C 코드)*:
    - `[관련 C 코드 경로:라인]`
  - *참조 (TC/Spec)*:
    - `[관련 TC 번호 또는 Spec 요구사항 ID]`
  - *목표*: [구체적인 완료 조건]
  - *작업*:
    - [수행할 구체적인 작업]
  - *검증 체크포인트*:
    - ... (기존 내용) ...

2. /speckit.taskstoissues 동작 재정의 (또는 가이드)
taskstoissues 에이전트는 tasks.md의 한 태스크를 bd 이슈로 변환할 때, 아래와 같은 구조화된 description을 생성해야 합니다.
bd create 시 description 필드 생성 규칙:
 Task: [태스크 이름]

[tasks.md의 '목표' 내용]

> 예를 들어, "LED의 상태는 HubState의 파생물일 뿐이다..." 와 같은 핵심 개념을 직접 넣어줍니다.
```

#### 현재 패러다임 (명령-복종) {#현재-패러다임--명령-복종}

```text
인간: "Phase 3 해주세요"
에이전트: (작업)
인간: "검증해주세요"
에이전트: (검증)
인간: "bd 업데이트해주세요"
에이전트: (업데이트)
인간: "Phase 4 해주세요"

```

문제:

-   인간이 매번 다음 단계를 지시해야 함
-   에이전트는 수동적 도구
-   컨텍스트가 끊기면 처음부터


#### 새로운 패러다임 (존재대존재) {#새로운-패러다임--존재대존재}

```text
인간: "진행하세요"
에이전트: (상태 확인 → 결정 → 실행 → 검증 → 다음...)
에이전트: "X 결정이 필요합니다"
인간: (결정)
인간: "진행하세요"
에이전트: (계속...)
```

특징:

-   인간의 입력은 "진행하세요" 하나뿐
-   에이전트가 자율적으로 다음 스텝 결정
-   막히면 결정 요청, 안 막히면 계속 진행
-   페이즈, 스텝, 상태에 관계없이 동일한 커맨드


### 핵심 원칙들 {#핵심-원칙들}


#### 1. Python 코드가 필요 없다 {#1-dot-python-코드가-필요-없다}

validate_phase.py 같은 검증 코드는 또 다른 유지보수 대상. 스펙이 바뀌면 코드도 바뀌어야 함.

진정한 SDD:

-   스펙이 검증 기준 그 자체
-   에이전트가 스펙을 읽고 판단
-   "YAML이 파싱되는가?"는 에이전트가 직접 확인 가능
-   "필드 수가 맞는가?"도 에이전트가 세면 됨


#### 2. bd는 메모리 시스템 {#2-dot-bd는-메모리-시스템}

bd는 인간에게 명령하는 것이 아님. 에이전트가 자율적으로 사용하는 메모리.

```bash
# 에이전트가 알아서:
bd ready      # 다음 할 일 파악
bd update     # 진행 상태 기록
bd close      # 완료 표시
bd show       # 컨텍스트 복원

# 인간이 필요할 때:
bd show sks-8it   # "현재 어디까지 왔어?"
bd blocked        # "뭐가 막혔어?"
```


#### 3. 하루 원칙 {#3-dot-하루-원칙}

> "멀티 에이전트로 진행한다면 규모에 큰 구애 없이 하루 안에 다 정리가 되어야 합니다. 만약 하루 안에 못한다면 그 작업은 스펙에 문제가 있는 것이며 이 경우 일정을 잡는 것은 무의미합니다."


#### 4. 표준 프로세스 루프 {#4-dot-표준-프로세스-루프}

스펙 생성 및 검증, 환경 정의 등이 끝나면 그 뒤 작업은 표준 프로세스 루프 안에서 해결.


#### 5. 토큰 효율 {#5-dot-토큰-효율}

> "룰은 결국 토큰을 아끼는 최선의 방법"

명확한 스펙 + 표준 커맨드 = 컨텍스트 최소화 = 토큰 절약
