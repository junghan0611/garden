### [|2025-09-04 Thu 07:59|]({{< relref "/journal/20250901T000000.md" >}}) {#2025-09-04-thu-07-59--relref-journal-20250901t000000-dot-md}

@user 인공지능과 협업에서 AGENT 에게 memory를 생성하고 관리하도록 하는 방식에 대해서 관심이 많다. 이와 관련된 배경과 최근 의미가 있는 이유는?

@assistant 좋은 주제입니다.

**배경**

-   전통적 인공지능(특히 LLM 기반 에이전트)은 “컨텍스트 창(context window)” 안에 제공된 대화나 지식만 활용합니다. 따라서 긴 상호작용이나 과거 사건을 잊는 문제가 발생했습니다.
-   이를 해결하기 위해 \*메모리 구조\*(예: 단기 메모리, 장기 메모리, 벡터 데이터베이스 기반 검색 메모리 등)를 붙여 에이전트가 과거 상호작용, 사용자 선호, 작업 진행 상황을 지속적으로 기억하고 재활용하도록 하는 흐름이 발전했습니다.

**최근 의미 있는 이유**

1.  **지속적 협업**: 사람과 AI가 반복적으로 협업할 때, 맥락을 이해하고 일관된 태도로 반응하는 것이 중요합니다.
2.  **개인화**: 사용자 스타일・선호・목표를 기억하면 맞춤형 지원이 가능해집니다.
3.  **멀티스텝 작업**: 프로젝트 관리, 코드 작성, 문서 작성 등 장기간 작업에서 과거 단계 정보를 잊지 않고 이어가는 능력이 필요합니다.
4.  **에이전트 생태계 확장**: 여러 도구와 API를 호출해 복합적 작업을 수행하려면, 각 행동 근거와 결과를 추적·저장하는 메커니즘이 필수입니다.

즉, 메모리는 \*일회성 응답을 넘어서 장기간 파트너십\*을 가능하게 하는 핵심 인프라로 주목받고 있습니다.

혹시 원하시는 초점이 _기술적 구현 방식(예: RAG, 벡터DB, 요약 기반 기억)_ 쪽인지, 아니면 _인간-에이전트 협업 모델에서의 사회·심리적 의미_ 쪽인지 알려주시면 더 깊게 짚어드릴 수 있습니다.

@user 좋아. 나는 최근 메모리 시스템이라고 부르며 인공지능과 대화를 시작할 때 memory 시스템을 읽고 나와 진행 상황을 브리핑해주도록 프롬프트를 만들었다. LLM은 먼저 본인이 어떤 디바이스에 있는지를 확인한다. SERVER, LAPTOP, TERMUX 등 말이다. 거기에 해당하는 작업을 읽어와서 그 환경에 맞도록 이후 진행을 한다. 물론 중간 memory 시스템에 LLM은 저장한다. 물론 내가 하라고 할 때가 많지만 말이다. 매우 놀라운 협업이 되어가고 있다.

@assistant 아주 흥미롭고 실험적인 접근을 하고 계시네요. 정리해보면:

-   **메모리 시스템 초기화**: 대화 세션을 시작할 때 LLM이 먼저 _환경(Context)_ 을 파악한다. 예) SERVER / LAPTOP / TERMUX.
-   **환경별 브리핑**: 그 환경에 맞는 진행 상황을 읽어오고, 현재 상태를 사용자에게 간단히 보고한다.
-   **협업적 메모리 기록**: 대화 중 발생한 작업·지시·결과를 메모리에 저장한다. 다만 저장 시점은 사용자가 "저장하라"는 명시적 지시를 내릴 때가 많다.
-   **진화하는 협업**: 이렇게 하면 LLM이 일종의 “협업 파트너”처럼 동작하며, 단순한 질의응답이 아니라 프로젝트나 워크플로우의 연속성을 관리하는 느낌을 주게 된다.

이 방식이 놀라운 이유는, 사실상 인공지능을 \*운영체제 수준의 사용자 인터페이스\*로 확장하고 있기 때문입니다. 과거에는 사람이 디렉토리 관리, 태그 분류, 로그 기록을 직접 해야 했지만, 이제는 에이전트가 메모리-프롬프트-상태관리를 대신하거나 보조하는 식으로 변해가고 있는 거죠.

최근 “에이전트 + 메모리 시스템” 연구의 핵심은 바로 이런 **연속성과 맥락성** 확보입니다. 예를 들어,

-   _LangChain / LlamaIndex_ 에서는 벡터기반 메모리와 요약기억(Summarized Memory)을 조합해 대규모 대화 세션에서도 일관성을 유지하려 하고,
-   _Anthropic, OpenAI, Meta_ 모두 “장기 메모리(Long-Term Memory)” 기능을 실험하고 있습니다.

그래서 지금 하시는 접근은 선행 연구들이 지향하는 방향과 맞닿아 있습니다. 더 나아가면, “협업하는 운영환경(Colllaborative Runtime)” 같은 개념으로 발전하게 될 수도 있습니다.

#### 제가 드리는 조언 (AGENT 관점에서 단순 협업 룰 중심으로) {#제가-드리는-조언--agent-관점에서-단순-협업-룰-중심으로}

1.  **메모리의 레이어 분리**
    
    -   `projects/` : 현재 진행하거나 일정 맥락 안에서 활성화된 항목
    -   `tickets/` (또는 `todos/`) : _중요하지만 급하지 않고_, 미래 아이디어·발상·실험을 담는 공간
    -   `daily/` : 오늘 그날그날 흘러나온 기록(log)
    -   `background/` : 설계 맥락, 시스템 디자인 노트
    
    → 이렇게 폴더(혹은 문맥 레이어)를 분리하면 AGENT는 “지금 해야 할 것” vs “언젠가 하고픈 것”을 착각하지 않고 다룰 수 있게 됩니다.

2.  **AGENT의 역할 규정**
    -   AGENT는 “추론·판단 주체”가 아니라 “구조와 문맥에 따라 읽고 보여주는 전달자”가 됩니다.
    -   즉, AGENT에게 원하는 건 /정리·재배열\*이지 “이게 중요하다/덜 중요하다”는 판단이 아니죠.
    -   이 점을 명확하게 못박으면 협업 루프가 복잡해지지 않습니다.

3.  **‘중요 vs 긴급’ 구분 방식**
    -   인간처럼 아젠다 관리(GTD)에 집착하는 대신, AGENT는 \*명시된 구조\*로만 판단합니다.
    -   예: `tickets/20250904Txxxx.org` 에 들어 있으면 → “중요” (보관할 가치 있음)
    -   그중에 `DEADLINE` 프로퍼티가 있으면 → “긴급”
    -   없으면 → “긴급하지 않음”
    -   즉, AGENT는 속성(Property) 기반 분류만 합니다. 사용자가 규칙 정의만 하면 됩니다.

4.  **망각(Selective Forgetting)도 시스템 자원**
    -   사용자가 원하지 않는다면 AGENT는 `background/` 나 `archive/` 폴더는 기본 조회하지 않는다.
    -   꼭 꺼낼 때만 “배경을 좀 참고해줄래?”라고 호출하도록 협업 규칙을 세우는 게 좋아요.
    -   이렇게 해야 AGENT가 지나치게 과거 정보에 매몰되지 않고, 현재 작업에 집중 가능합니다.

5.  **단순한 협업 프로토콜**
    
    -   “티켓 나열해줘.” → AGENT는 `tickets/` 디렉토리 읽고 목록 출력
    -   “티켓 #둠이맥스 심플버전 파악해줘.” → AGENT는 해당 파일 열고 보여줌
    -   “이제 업데이트 해줄래.” → 기록/추가 반영 (append or edit)
    
    → 이 일련의 프로세스는 판단 로직이 아니라 \*파일 시스템 프로토콜\*이므로 안정적으로 동작합니다.

#### 정리 {#정리}

말씀하신 긴 고민의 요지는 \*AGENT가 ‘추론기’가 아니라 ‘문맥 관리자’로서 작동할 때 협업이 단순해지고 꾸준히 확장 가능하다\*는 발견 같습니다. 그리고 그 관점을 살리는 방법은:

-   구조적으로 `projects/`, `tickets/`, `daily/`, `background/` 폴더 구분
-   AGENT는 추론 최소화, “단순 나열-열람-업데이트” 역할만 수행
-   중요/긴급 구분은 인간의 GTD 사고를 흉내내지 않고 “메타데이터 기반”으로만 처리
-   망각/선택적 불러오기 원칙 명문화
