## HomeAgent — 오픈소스 스마트홈 에이전트 플랫폼 {#homeagent-오픈소스-스마트홈-에이전트-플랫폼}


### 비전 {#비전}

> 달에 보내도 동작할 자립형 시스템. 클라우드 없이, 프라이버시를 지키며, 에이전트와 협업하는 스마트홈.

RPi5 위의 Go 바이너리 하나로 Matter 디바이스를 제어하고, on-device sLLM이 자연어로 집을 관리한다. 이것은 단순한 스마트홈 허브가 아니라, 오프라인 에이전트 협업의 물리적 거점이다.


### 현재 상태 (2026-03-07) {#현재-상태--2026-03-07}


#### 기술 스택 {#기술-스택}

| 레이어  | 기술                           | 비고                    |
|------|------------------------------|-----------------------|
| OS      | Yocto Scarthgap 5.0 LTS        | 재현 가능한 이미지      |
| 허브    | Go (단일 바이너리, ~7MB)       | 상태관리, SSE, 에이전트 |
| Matter  | matter.js (Node.js)            | BLE 커미셔닝, Thread+WiFi |
| 프론트엔드 | Lit WebComponents (~40KB)      | Vite 빌드               |
| AI 에이전트 | OpenRouter / on-device sLLM    | Gemini Flash ~$0.02/day |
| 하드웨어 | RPi5 + Thread RCP (RCP dongle) | OTBR 내장               |


#### 검증된 기능 {#검증된-기능}

-   Matter over Thread: Tuya Door Sensor x2
-   Matter over WiFi: Tapo Smart Plug x1
-   LLM 에이전트: 자연어 → 디바이스 제어 ("플러그 꺼줘")
-   실시간 SSE 이벤트 스트리밍
-   A2UI: 서버 결정 테마 (시간대별 자동 전환)
-   REST API 8 commands (on/off/level/color/color_temp/thermostat/lock/unlock)
-   Flutter Linux Desktop 빌드 ✅
-   Android APK (43.7MB) + Go arm64 (7.2MB) ✅
-   Yocto flutter-engine 빌드 ✅


### 로드맵: 해야 할 것들 {#로드맵-해야-할-것들}


#### 0. Go TUI — 터미널 대시보드 (2026-03 추가) {#0-dot-go-tui-터미널-대시보드--2026-03-추가}

charmbracelet 스택(bubbletea + lipgloss + cobra)으로 터미널 대시보드 구축. 디바이스 리스트/제어, 실시간 이벤트, LLM 채팅을 터미널에서. robot mode(JSON stdout)로 에이전트 연동.

기능 검증의 첫 번째 인터페이스. TUI에서 검증 → Web/APK에 반영.

상태: ✅ 실기기 연결 검증 완료 (2026-03-08). cobra+bubbletea+lipgloss 475줄.


#### 1. 크로스플랫폼 앱 — Go + Flutter {#1-dot-크로스플랫폼-앱-go-plus-flutter}

현재: Lit 웹앱 (브라우저 전용) 목표: Linux + Android 양쪽에서 동작하는 네이티브 앱

Go(백엔드) + Flutter(프론트엔드)로 하면:

-   Linux (RPi5, NixOS): 네이티브 앱
-   Android (월패드, 태블릿): 네이티브 앱
-   meta-flutter (Yocto 레이어)로 임베디드 배포 가능

코틀린은 건드리지 않는다. Go, Zig, TypeScript, Bash로 충분하다. connectedhomeip(CHIP SDK)에서 matter.js로 통일하면 두 플랫폼의 Matter 스택이 같아진다.


#### 2. sLLM 튜닝 — on-device 에이전트 {#2-dot-sllm-튜닝-on-device-에이전트}

현재: OpenRouter 경유 Gemini Flash 목표: RPi5 위에서 3B~7B 모델이 로컬 추론

-   디바이스 제어 특화 fine-tuning
-   인터넷 없이도 "불 꺼줘"가 동작
-   클라우드 에이전트(glg)와 연결될 때 동기화


#### 3. A2A 프로토콜 — 에이전트 간 통신 {#3-dot-a2a-프로토콜-에이전트-간-통신}

Agent-to-Agent.

-   homeagent의 로컬 에이전트 ↔ 클라우드 에이전트(glg, gemini)
-   디바이스 이벤트를 에이전트 네트워크로 전파
-   어젠다 타임라인에 IoT 이벤트가 함께 찍히는 세계


#### 4. A2UI — 에이전트 생성 UI {#4-dot-a2ui-에이전트-생성-ui}

현재: 서버(Go)가 팔레트 결정 → CSS 변수 주입 목표: LLM이 UI 컴포넌트를 선언적으로 생성


#### 5. Yocto 이미지 재현성 {#5-dot-yocto-이미지-재현성}

SD 카드 플래싱 → 부팅 → 동작. NixOS의 재현가능성 철학과 같은 맥락. npm-shrinkwrap 관리, 오프라인 빌드 지원이 핵심.


### 생존과 로드맵의 일치 {#생존과-로드맵의-일치}

> 생존해야 되니까 하는 회사 일과 나의 로드맵을 일치시켜야지. 그렇게 해야 가든에 공개가 가능하고 포트폴리오로 기술 커리어를 드러낼 수 있을 것 같아. — 정한, 2026-03-04

회사가 필요로 하는 것(월패드 앱, Matter 디바이스 제어)과 내가 꿈꾸는 것(오프라인 에이전트 플랫폼)이 homeagent-config에서 만난다.

산출물은 오픈소스로. 회사는 로고 박고 필요한 것 넣어서 가져간다. 시간을 파는 것이 아니라, 자기 로드맵 위에서 일하는 것.


### fxf-uho-mvt와의 관계 {#fxf-uho-mvt와의-관계}

fxf-uho-mvt (Zigbee 허브, 22대 DS/SP/LIG 운용)는 레거시 프로토콜 영역. homeagent-config (Matter 허브)는 차세대 프로토콜 영역. 둘 다 "자립형 허브"라는 같은 철학 위에 있다.

fxf-uho-mvt에서 검증한 것들 — 상태머신 설계, configureReporting, 오프라인 복원 — 이 경험이 homeagent-config의 Matter 레이어에 흘러들어간다.

## Go TUI — 인터페이스의 첫 번째 계층 {#go-tui-인터페이스의-첫-번째-계층}


### 왜 TUI인가 {#왜-tui인가}

> 만들 때는 TUI로 만들면 충분히 빠르게 기능들을 검증할 수 있어. Go는 정말 특이한 분야 아니라면 우리에게 최적의 언어. — 정한, 2026-03-07

Flutter 앱이든, 웹이든, 음성이든 — 최종 인터페이스는 다양하다. 하지만 기능 검증의 가장 빠른 경로는 TUI다:

-   ****즉시 피드백****: 컴파일 → 터미널에서 바로 확인
-   ****API 직결****: Go 바이너리 안에 서버 + TUI가 공존. 같은 코드, 같은 타입
-   ****SSH 접근****: RPi5에 SSH로 접속해서 TUI로 디바이스 제어 — 브라우저 불필요
-   ****에이전트 친화****: robot mode (JSON stdout)로 에이전트가 TUI 없이도 활용

인터페이스 계층:

```text
TUI ──┐
Web ──┼── Go REST API ── matterjs-server ── 디바이스
APK ──┘
```

연결은 TUI에서 먼저 검증하고, 확인되면 Web/APK에 붙인다.

-   Graph view: 의존성 DAG 시각화

-   Kanban → 방별 디바이스 보드?
-   beads 생태계(br)와 같은 뿌리 — 이슈 관리 + TUI 뷰어 조합


### HomeAgent TUI 구상 {#homeagent-tui-구상}

```text
cobra 서브커맨드 구조:
  homeagent serve         # HTTP 서버 (기존)
  homeagent tui           # 대시보드 TUI (새로)
  homeagent devices       # 디바이스 목록 (CLI/robot)
  homeagent control       # 디바이스 제어 (CLI)
  homeagent status        # 상태 요약 (CLI/robot)
```

안전한 영역:

-   순수 JS 실행 (V8 glibc userland 완결)
-   네트워크 I/O (HTTP/TCP/UDP — kernel syscall 동일)
-   파일시스템, 시리얼 포트 (/dev/ttyS5 fd=18 검증)
-   프로세스 관리 (fork/exec — kernel ABI)

잠재 리스크:

-   DNS 해석: glibc getaddrinfo → /etc/resolv.conf (Android 경로 다름)
-   TLS/SSL: 시스템 CA 인증서 경로 차이
-   SELinux: userdebug OK, user 빌드에서 /data/local/tmp 차단 가능
-   BLE: noble → Linux HCI 소켓 필요 → Android 불가

한계:

-   Android Bluetooth API 접근 불가 (Binder IPC)
-   프로덕션 배포 시 SELinux policy 추가 필요


### Android BLE 블로킹 — 원인과 해결 {#android-ble-블로킹-원인과-해결}

원인:

-   RPi5: BlueZ → hci0 커널 등록 → AF_BLUETOOTH 소켓 → noble ✅
-   RK3576: Android BT HAL 1.0 → hci0 미등록 (userspace 직접 관리) → noble ❌

HA Android의 비밀:

-   `com.google.android.gms.home.matter.Matter` (Google Play Services)
-   앱이 BLE를 직접 다루지 않음 — GMS가 전부 처리
-   서버는 `commissionOnNetworkDevice(passcode, ip)` 만 호출

```javascript
discoveryCapabilities: {

  onIpNetwork: true                         // IP 기반은 항상 true
}
```

## BLE 커미셔닝 — A안(Dart 풀스택) vs B안(matterjs Remote BLE) (2026-03-08) {#ble-커미셔닝-a안--dart-풀스택--vs-b안--matterjs-remote-ble----2026-03-08}


### 문제의 본질 {#문제의-본질}

Android에서 BLE를 쓰려면 Android BLE API가 필요하다. RPi5/Linux는 noble(HCI 소켓)로 해결되지만, Android BT HAL은 hci0를 커널에 등록하지 않는다. 따라서 Flutter가 BLE를 다뤄야 하는 것은 ****어쩔 수 없다.****

문제는 ****프로토콜 로직을 어디에 둘 것인가.****


### A안: Dart에서 전부 구현 (현재) {#a안-dart에서-전부-구현--현재}

```text
Flutter (Dart ~800줄)
  BLE scan/connect
  BTP handshake + segmentation
  Spake2+ (PASE)
  AES-128-CCM (SecureSession)
  NetworkCommissioning TLV (WiFi)
  → Go Hub REST (commission_with_code, network_only=true)
    → matterjs-server (IP-only CASE)
```

-   장점: 외부 의존 없음, 자립형
-   단점: Matter spec 변경 시 Dart 코드 수정 필요, 자체 crypto 검증 부담
-   현재 상태: 구현 완료, 테스트 39개 통과, 실기기 BTP 핸드셰이크 디버깅 중


### B안: Flutter = BLE 파이프, matterjs가 프로토콜 전부 처리 {#b안-flutter-ble-파이프-matterjs가-프로토콜-전부-처리}

```text
Flutter (Dart ~100줄)             matterjs-server
  BLE scan/connect                  ↕ WebSocket
  C1.write(bytes) ←──── WS ────── RemoteBleInterface
  C2.indicate(bytes) ──── WS ───→   implements ConnectionlessTransport
  BLE disconnect                    BTP + PASE + WiFi + CASE 전부 기존 코드
```

-   장점: Dart 프로토콜 코드 0줄, npm update로 Matter spec 대응, matterjs 검증 수준 그대로
-   단점: matterjs-server 코드 수정 필수


### 핵심 발견: @matter/nodejs-ble {#핵심-발견-matter-nodejs-ble}

`@matter-server/ws-controller` 의 의존성 구조:

| npm registry (실제)    | shrinkwrap (Yocto용)   |
|----------------------|-----------------------|
| optionalDependencies   | dependencies로 이동됨  |
| → `@matter/nodejs-ble` | → `@matter/nodejs-ble` |

-   Yocto shrinkwrap: dependencies로 들어있어서 오프라인 빌드 시 **설치됨** ✅
-   bundle-backend.sh: shrinkwrap 안 쓰고 `npm install` 직접 → optional이라 **안 깔림** ❌


### B안 정밀 분석 — 안 될 수 있는 이유 (2026-03-08 정밀 리서치) {#b안-정밀-분석-안-될-수-있는-이유--2026-03-08-정밀-리서치}


#### 위험 1: `@matter/nodejs-ble` 를 그대로 쓸 수 없다 ⚠️ (수정 필요) {#위험-1-matter-nodejs-ble-를-그대로-쓸-수-없다-️--수정-필요}

초기 가설: "noble 대신 WS relay로 교체하면 된다" → **부정확**

`@matter/nodejs-ble` 등록 메커니즘:

```text
import "@matter/nodejs-ble"               ← MatterController.js 23행
  → install.ts: ServiceBundle.default.add(nodejsBle)
    → env.vars.boolean("ble.enable") 체크
      → env.set(Ble, new NodeJsBle())
        → NodeJsBle.centralInterface → new NobleBleCentralInterface(scanner)
                                         → noble import 필요!
        → NodeJsBle.scanner → new BleScanner(new NobleBleClient())
                                         → noble import 필요!
```

`NodeJsBle` 는 lazy initialization이지만, `centralInterface` 호출 시 `NobleBleCentralInterface` → `BleScanner` → `NobleBleClient` → `@stoprocent/noble` ****noble native 바이너리가 없으면 import 시 크래시.****

따라서 `@matter/nodejs-ble` 를 import하는 것이 아니라, \*=Ble= 추상 클래스의 새 서브클래스 `RemoteBle` 를 만들어 통째로 교체\*해야 한다.


#### 위험 2: `Ble` 교체 가능한가? ✅ 가능 {#위험-2-ble-교체-가능한가-가능}

```text
Ble (추상 클래스, @matter/protocol)
  ├── abstract centralInterface: ConnectionlessTransport
  ├── abstract scanner: Scanner
  └── abstract peripheralInterface: BlePeripheralInterface

등록: env.set(Ble, instance)
사용: env.get(Ble).centralInterface → ConnectionlessTransportSet.add()
```

`ServiceBundle` 기반이므로 나중에 `env.set(Ble, remoteBle)` 하면 덮어쓰기 가능. 또는 `import "@matter/nodejs-ble"` 줄을 제거하고 커스텀 `RemoteBle` 만 등록.


#### 위험 3: BLE 스캔도 교체 필요 ⚠️ (추가 작업) {#위험-3-ble-스캔도-교체-필요-️--추가-작업}

`ControllerBehavior.initialize()` (79행):

```javascript
env.get(ScannerSet).add(env.get(Ble).scanner)    // BLE 스캔 등록
netTransports.add(env.get(Ble).centralInterface) // BLE transport 등록
```

→ `scanner` 도 커스텀 `RemoteBleScanner implements Scanner` 필요. Flutter가 BLE 스캔 결과를 WS로 전달 → `RemoteBleScanner` 가 디바이스 목록 관리.


#### 위험 4: WS latency가 BTP 타이밍을 깨는가? ✅ 안전 {#위험-4-ws-latency가-btp-타이밍을-깨는가-안전}

| BTP 타이밍             | 값  | localhost WS |
|---------------------|----|--------------|
| `BTP_CONN_RSP_TIMEOUT` | 5초 | ~1ms         |
| `BTP_ACK_TIMEOUT`      | 15초 | ~1ms         |
| `BTP_SEND_ACK_TIMEOUT` | 5초 | ~1ms         |

같은 기기 내 localhost WS relay는 ms 단위. BTP 타이밍 여유 충분.


#### 위험 5: BTP 핸드셰이크가 BLE 물리 레벨 문제면? ⚠️ A/B 공통 {#위험-5-btp-핸드셰이크가-ble-물리-레벨-문제면-️-a-b-공통}

A안 BTP 타임아웃 원인이:

-   **Dart BTP 코드 버그** → B안에서 해결 (matterjs 검증 코드)
-   **Android BLE API 문제 (C2 indicate 안 옴)** → B안도 같은 증상
-   **TP-Link P100이 BTP 미지원** → A/B 둘 다 안 됨

### 추가 위험: "유일한 경우"가 유일하지 않다 (2026-03-08 추가 리서치) {#추가-위험-유일한-경우-가-유일하지-않다--2026-03-08-추가-리서치}


#### 위험 6: `ble.enable` 활성화 경로 ⚠️ {#위험-6-ble-dot-enable-활성화-경로-️}

```javascript
// MatterServer.js:64
if (cliOptions.bluetoothAdapter !== null) {
  env.vars.set("ble.enable", true);  // CLI --bluetooth-adapter 있을 때만!
}
```

Android에 hci0 없음 → `--bluetooth-adapter` 전달 안 하면 `ble.enable=false` → BLE 커미셔닝 비활성화. 해결: RemoteBle install.js에서 `env.vars.set("ble.enable", true)` 강제 설정.


#### 위험 7: WiFi credentials 전달 경로 {#위험-7-wifi-credentials-전달-경로}

```javascript
// WebSocketControllerHandler.js:468
if (!network_only && this.bleEnabled) {
  wifiCredentials = { wifiSsid: config.wifiSsid, wifiCredentials: config.wifiCredentials };
}
```

BLE 커미셔닝 시 WiFi 정보를 matterjs config에서 자동으로 가져옴. Go `set_wifi_credentials` WS 명령으로 커미셔닝 전에 설정 필요. Flutter UI → Go REST → matterjs WS `set_wifi_credentials` 흐름 연결 필요.


#### 위험 8: `import "@matter/nodejs-ble"` 제거 방법 {#위험-8-import-matter-nodejs-ble-제거-방법}

`MatterController.js:23` 은 npm 패키지 내부 파일 — 직접 수정하면 npm update 시 덮어씀.

추천 해결: `@matter/nodejs-ble` \*\*더미 패키지\*\*로 대체

```javascript
// node_modules/@matter/nodejs-ble/dist/esm/index.js (더미)
export {};  // noble import 없이 빈 모듈
```

import 에러 없이 로드, install.ts의 ServiceBundle 등록 안 됨. RemoteBle가 대신 등록.


#### B안 위험 전체 정리 {#b안-위험-전체-정리}

| # | 위험                 | 대응                         | 난이도 |
|---|--------------------|----------------------------|-----|
| 1 | noble import 크래시  | 더미 패키지 대체             | 쉬움 |

| 4 | WS latency           | localhost ~1ms, BTP 5~15초   | 안전 |

#### 위험 9: `network_only` 플래그 반전 필수 🔴 (GPT도 놓침) {#위험-9-network-only-플래그-반전-필수--gpt도-놓침}

현재 Go: `args["network_only"] = true` (A안: Flutter가 BLE, matterjs는 IP-only) B안: matterjs가 BLE 전부 → `network_only = false` 여야 함.

```javascript
// WebSocketControllerHandler.js:468
if (!network_only && this.bleEnabled) {
  wifiCredentials = { ... };  // network_only=true면 WiFi 안 붙음!
}
```


#### 위험 10: BleScanner 상속 불가 — Scanner 처음부터 구현 {#위험-10-blescanner-상속-불가-scanner-처음부터-구현}

`BleScanner` 는 `@matter/protocol` 에 없음. `@matter/nodejs-ble` 패키지 자체에 190줄. noble(`NobleBleClient`)에 직접 의존. `Scanner` 인터페이스를 처음부터 구현해야 함. ~80줄 예상 → **~150줄**.

### 판단 (최종) {#판단--최종}

1.  A안 E2E 실패 → B안 전환 결정
2.  B안은 "noble API를 WS로 래핑"이 아니라 "`Ble` 추상 클래스 통째로 교체"
3.  `@matter/nodejs-ble` 는 더미 패키지로 대체 (noble 제거)
4.  RemoteBle install.js에서 `ble.enable` 강제 설정 + `env.set(Ble, remoteBle)` 등록
5.  WiFi credentials는 Go `set_wifi_credentials` → matterjs config 경로 사용
6.  bundle-backend.sh에서 `@matter/nodejs-ble` 더미 패키지 + RemoteBle 코드 배치

삽질 아님. A안이 BLE 프로토콜 이해의 기반. B안 전환 시 matterjs 내부 구조 파악이 선행 조건이었고 그게 이 리서치.
